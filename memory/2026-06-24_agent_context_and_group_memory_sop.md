# 2026-06-24 Agent 上下文与群聊记录治理 SOP

## 文档目的

本文用于指导 `btd6bot_plugin` 后续对大模型 Agent 的上下文管理、群聊记录管理、输出智能度和输出稳定性进行持续改造。

目标不是一次性写完方案，而是作为长期执行 SOP 使用：

- 明确总目标。
- 明确分阶段实施方式。
- 明确每阶段验收标准。
- 明确阶段完成后如何更新现状、风险和下一阶段计划。

本文默认是该主题的主追踪文档。后续每完成一阶段，应优先更新本文；如阶段内容较大，可新增配套 phase 文档，但本文仍需回写摘要与状态。

## 总目标

### G1. 提升群聊场景下的理解能力

让 Agent 不再只依赖“当前消息 + 当前用户的短会话历史”，而是能够在需要时理解：

- 当前群最近在聊什么。
- 这条消息接的是谁、接的哪段上下文。
- 当前用户在本群里的连续任务是否尚未完成。
- 当前问题是闲聊、延续讨论、事实查询还是工具请求。

### G2. 提升输出稳定性

让 Agent 在相似输入下更稳定地：

- 判断是否应该回复。
- 判断是否应该调用工具。
- 选择正确工具和参数。
- 在拿到工具结果后按一致格式组织回复。

### G3. 控制上下文成本

在增强上下文能力的同时，避免上下文无限增长，控制：

- token 成本
- 延迟
- 历史噪音
- 错误记忆累积

### G4. 建立可持续演进的 SOP

后续每一轮改造都应能回答四个问题：

- 现在系统实际上如何工作。
- 本阶段改动了什么。
- 本阶段是否达到预期。
- 下一阶段做什么、为什么做。

## 当前现状（2026-10-12）

以下描述对应当前工作区实现，尚未部署；详细方案、验证结果和限制见 [上下文预算与持久记忆](2026-10-12_context_budget_and_persistent_memory.md)。

1. 主链路为 `Agent = Model + Harness`，使用原生 `tools/tool_calls`。下文 Phase 4/5 的 planning/rendering 是历史实现记录，不再描述当前运行方式。
2. 主输入包含系统提示、工具 schema 和结构化 `reply_context`（当前事件、会话摘要/原轮次、最近群窗口、检索记忆）。会话历史不再作为额外一整份重复注入。
3. 每次 Agent 模型调用应用默认 24000 token 的估算输入预算。知识默认按 8000 字符选取证据/分页，保留标题、表头、来源及原始工具配对。显式长文读取能力保留，模型 observation 独立受预算限制。
4. 会话默认超过 12000 字符尝试摘要，保留轮数与用户历史窗口对齐（默认 6），摘要整体默认最多 1200 字符。未摘要历史不提前隐藏；无效摘要和服务故障保留原记录，积压历史按预算分批摘要。
5. 群窗口默认最多 10 条、4000 字符，只选近 24 小时消息或窗口内明确引用的消息，与用户会话去重。历史图片只在视觉追问/明确引用时选用；引用目标优先，缓存过期则文本降级。
6. 新增现有 SQLite 内的轻量持久层，按群/用户恢复会话并召回历史用户原文；显式偏好、任务和管理员群规则带来源、更新时间和过期时间，支持同 key 更新和删除。助手旧答案不会作为已确认游戏事实召回。
7. 记忆工具只暂存变更，成功交付回复后原子提交。失败发送不提交；交付后存储失败有单独状态与提示，保留本进程中的已发送会话，不自动重放显式记忆变更。
8. 当前使用本地词项相关性检索；暂未引入向量数据库、图记忆或外部 memory 服务。后续以召回失败样例和回答质量对照决定是否升级。

下文保留 2026-06-24 的阶段计划、实现和当时验收记录，便于追踪设计演化；其中“当前”“下一阶段”均对应该阶段完成时点。最新行为以前述现状和 2026-10-12 配套记录为准。

## 总体实施策略

本次治理遵循以下原则。

### P1. 先增强“相关上下文”，再增加“更多上下文”

优先把模型真正需要的上下文送进去，而不是机械增加历史长度。

### P2. 先稳定决策，再优化文风

先让模型更稳定地做对，再考虑如何更自然地说出来。

### P3. 先建立数据契约，再扩充记忆能力

没有清晰的数据结构，后续越做越乱。先定义上下文对象、群聊窗口对象、摘要对象的字段，再逐步替换旧实现。

### P4. 每阶段都必须可回退、可验证

每阶段改动都要：

- 可局部上线
- 可做对照验证
- 可在日志中观察

## Phase 1：上下文数据契约重构

### 目标

把“当前消息、用户短期记忆、群聊窗口、压缩摘要”从松散文本拼接，重构为清晰的数据契约。

### 实现方式

1. 定义主回复上下文对象，至少包括：
   - current_event
   - user_session_memory
   - recent_group_window
   - policy_hints
2. 定义用户会话摘要对象，建议至少包括：
   - user_preferences
   - open_loops
   - established_facts
   - recent_topic
3. 定义群聊窗口对象，建议至少包括：
   - message_id 或顺序位
   - speaker
   - cleaned_text
   - created_at
   - mention_relation
4. 替换当前“整段事件 JSON 原样入历史”的做法，改为更紧凑的内部表示。

### 为什么先做这一阶段

后续无论是接入群上下文、做更智能压缩，还是做 plan/render 两阶段，都需要先有统一的数据结构，否则会持续在 prompt 里塞临时字符串。

### 预期收益

- 降低上下文噪音。
- 提高模型对重点信息的利用率。
- 为后续结构化压缩和检索打基础。

### 风险

- 一次性替换过大可能影响现有行为。
- 需要保留兼容路径，避免现网回答风格剧烈跳变。

### 验收标准

- 主上下文构造逻辑中不再直接把完整 event JSON 作为长期历史的唯一表达。
- 新增结构化上下文对象定义。
- 日志中能看到主要上下文字段，而不是只能看到大段未分层 JSON。

## Phase 2：接入群聊窗口上下文

### 目标

让 Agent 在决定是否回复、如何回复前，能看到同群最近一小段高相关消息窗口，而不是只看当前用户自己的历史。

### 实现方式

1. 在数据库读取层增加“最近群消息窗口”接口，支持：
   - 条数限制
   - 噪音过滤
   - CQ 码清洗
   - 仅保留文本有效消息
2. 在主 Agent 调用前按需注入最近群聊窗口。
3. 先从固定窗口开始，例如最近 8 到 12 条，再逐步优化成条件触发。
4. 在主动接话模式下，将“最近群聊窗口”纳入是否 ignore 的决策依据。

### 为什么这一阶段优先级高

这是提升“群聊理解能力”的最大杠杆。很多看起来像模型笨的问题，本质上是模型没看到群上下文。

### 预期收益

- 更好理解代词、省略、接话。
- 更好判断当前话题。
- 主动接话时更少误触发。

### 风险

- 直接注入未清洗原始消息，会把噪音也带给模型。
- 窗口过长会增加成本和延迟。

### 验收标准

- 主 Agent 在日志中可观测到 recent_group_window 字段。
- 至少有一组测试覆盖“没有群窗口”和“有群窗口”下的差异场景。
- 主动接话误回复率下降。

## Phase 3：会话压缩结构化改造

### 目标

把当前“自由文本摘要”改为“结构化摘要 + 最近原始轮次”的混合记忆。

### 实现方式

1. 将压缩输出改成稳定字段，而不是单段自然语言。
2. 压缩提示词明确要求提取：
   - 用户偏好
   - 已确认事实
   - 未完成任务
   - 当前持续话题
   - 禁止/限制项
3. 调低压缩触发阈值，避免历史长期膨胀后才一次性压缩。
4. 保留最近若干轮原文，摘要只负责旧信息。

### 预期收益

- 压缩结果更稳定。
- 后续回答更容易对齐长期上下文。
- 避免“摘要越写越像自由发挥”。

### 风险

- 如果摘要字段设计不好，会引入新的幻觉记忆。
- 需要清晰区分“明确事实”和“模型猜测”。

### 验收标准

- 压缩结果具有稳定字段结构。
- 长对话后上下文长度受控。
- 连续多次压缩不会明显污染历史语义。

## Phase 4：决策与表达两阶段化

### 目标

把“要不要回复/调什么工具”和“如何把结果说出来”拆成两个步骤，以提高输出稳定性。

### 实现方式

1. 新增 planning 阶段：
   - 低温度
   - 只负责决策
   - 输出可验证结构
2. 新增 rendering 阶段：
   - 基于 planning 结果和工具结果组织最终回复
   - 控制文风和长度
3. 将工具结果中的 `extra_prompt` 约束集中用于 rendering，而不是混在全部阶段中。

### 预期收益

- 工具选择更稳定。
- 同类请求输出一致性更高。
- 可以更清楚地区分“决策错误”和“表达不好”。

### 风险

- 增加一次模型调用，带来额外成本和延迟。
- 需要谨慎设计两阶段接口，避免重复注入冗余上下文。

### 验收标准

- 决策阶段与表达阶段日志可区分。
- 同类问题工具选择稳定性明显提升。
- 输出格式波动下降。
